# フェーズ5要件定義書（リリース準備と保守性の向上）

## 目的とスコープ

フェーズ5の目的は、フェーズ4までで機能のそろったアプリを、公開して使ってもらえる形にすることです。あわせて、フェーズを重ねて増えたコードと文書を、今後の保守で迷わない形に整えます。音楽の生成と画面の機能は変えません。次の4点を検証します。

- 新しい名称で、GitHub Pages から誰でも開いて聴ける
- 主なブラウザで、キーボードだけでも支援技術からでも操作できる
- リファクタリングの前後で、同じシードの展開が変わらない
- フェーズごとの文書を消しても、現行の仕様を領域ごとの文書から引ける

本書の要件の番号（F-105 以降、N-19 以降）は、本書の中でだけ使います。本書はリリースの前に削除するので、コードとテストからは参照しません。

**フェーズ5に含むもの**

- アプリの名称の変更（GenDnB は既存のアーティスト名と重なるため）
- ブラウザで画面を操作して確かめる E2E テスト
- 展開を変えないリファクタリング（テストの並べ替え、大きなファイルの分割、フェーズの名前や要件の番号に頼ったコメントの書き換え）
- アクセシビリティへの対応
- 主なブラウザでの動作の確認と手当て
- 仮素材として合成したドラムサンプルの正式な採用
- LICENSE ファイル（Apache License 2.0）の配置
- フェーズごとの文書から、領域ごとの仕様の文書への移行と、フェーズごとの文書・ロードマップの削除
- `package.json` と README の更新
- GitHub Actions による CI/CD と、GitHub Pages への配布

**フェーズ5に含まないもの**

- 音楽の生成と画面の機能の追加や変更。アクセシビリティとブラウザの互換のための手当ては除く
- lint と formatter、favicon と OGP、起動や読み込みに失敗したときの表示の改善（ロードマップのフェーズ5に入れていないため）
- ページ独自のキーボードショートカット（フェーズ4のまま）。キーボードでの操作は、Tab での移動とボタンやスライダーの標準のキー操作で満たす
- メニューを閉じるボタン以外で閉じること（フェーズ4のまま）
- GitHub Releases の自動作成。リリースノートは利用者目線で手で書く
- 英語など、日本語以外の画面と文書

## 進め方

このフェーズの作業には、順序に意味があります。

1. **基準の記録**: リファクタリングの前に、v0.5.0 の生成結果の基準を記録する（F-107）。基準より後に記録すると、リファクタリングで変わった展開を正として固定してしまうため
2. **リファクタリングとテストの並べ替え**: 基準と一致することを確かめながら進める。テストの並べ替えの先は、仕様の文書と同じ領域の構成にする（F-108）
3. **名称の決定とリモートの作成**: 名称を決めてから、その名前で GitHub のリポジトリを作り、Pages に配布する。リポジトリ名が配布する URL になるため。リポジトリの作成と push は利用者が行う
4. **E2E テストと CI/CD**: 配布と同じ base path のビルドに対して E2E テストを回す
5. **アクセシビリティとブラウザの確認**: E2E テストで自動で確かめられる部分を先に固め、実機と支援技術での手動の確認を後に行う
6. **仕様の文書への移行**: リファクタリングの後に行う。文書に書く実装（モジュールの分担と型）を、分割した後の形で書くため
7. **フェーズごとの文書の削除**: 最後に行う。本書とフェーズ5の設計書も削除の対象なので、フェーズ5で決めたことも移行の対象にする

## E2E テスト

E2E テストは、画面の状態と操作を確かめます。音の中身（何が鳴るか、濁らないか）は、単体テストとシミュレーションと試聴で確かめます。ヘッドレスのブラウザでの音の出力は環境に左右され、テストが不安定になるためです。

| 対象 | 確かめること |
| --- | --- |
| 初期画面 | 再生と停止のボタン・音量・2行のメーター・シーケンサー・共有のボタン・メニューを開くボタンが並び、停止のボタンが押せない |
| 再生の状態 | 再生・一時停止・再開・停止で、ボタンの表示と押せるかどうか、BPM と初期キーの欄の操作の可否、累計の表示が、状態の表に従う |
| 表示の切り替え | シーケンサーとスペクトラムアナライザーを切り替えると、どちらか一方だけが見える |
| メニュー | 開くと右から出て、パラメーターとミキサーのタブを切り替えられ、閉じるボタンでだけ閉じる。ミキサーのミュートとソロの状態がボタンに出る |
| クエリ文字列 | `?seed=12345` で開くとシードの欄が 12345 になる。規則に合わない値では乱数のシードになる |
| 設定ファイル | `config.json` を返す配布先で、書いた値がパネルとミキサーに出る。壊れた JSON でも画面が起動し、状態表示に一言出る |
| 共有 | ダイアログが開き、URL がシードを含める・含めないの選択に従う。再生中は鳴っている展開のシードになる。外のクリック・閉じるボタン・Esc キーで閉じる |
| メディア操作 | ページが登録したメディア操作の処理を呼ぶと、画面のボタンと同じ状態の変化になる |
| 狭い画面 | 幅 320px と 375px で、ページが横にはみ出さない。シーケンサーが1小節を表示し、メニューが画面の幅いっぱいに広がる |
| キーボード | Tab キーだけで、再生の開始からメニューの開閉・共有のダイアログの開閉までを行える。メニューと共有のダイアログで、フォーカスの移り先が F-113 に従う |
| アクセシビリティの自動検査 | 初期画面・再生中・メニューを開いた状態・共有のダイアログを開いた状態で、自動検査のツールが違反を報告しない |

**E2E テストで確かめないもの**

| 対象 | 理由 | 代わりに確かめる方法 |
| --- | --- | --- |
| OS のメディアキー、ロック画面、通知 | テストから OS の操作を起こせない | ページの処理の呼び出しを E2E テストで、OS からの操作をブラウザの確認で |
| クリップボードへの実際のコピー | ブラウザによって、テストから権限を与えられない | 権限を与えられるブラウザだけで E2E テスト、ほかはブラウザの確認で |
| 音の出力 | 上に書いたとおり | 単体テスト・シミュレーション・試聴 |
| 実機の Safari・iOS・Android での動作 | Linux で動かす WebKit は Safari と同じではない | ブラウザの確認で |

## リファクタリング

リファクタリングでは、利用者から見た振る舞いを変えません。生成側と再生側で、確かめ方を分けます。

| 側 | 守ること | 確かめ方 |
| --- | --- | --- |
| 生成 | 同じシード・パラメーター・設定ファイルで、全パートのイベントと FX が v0.5.0 と一致する | F-107 の基準との一致を単体テストで |
| 再生 | 音・ミキサー・一時停止と再開・FX のオートメーションの振る舞い | 既存の単体テスト（オートメーション、ダッキング、再開位置、クリップ）、E2E テスト、v0.5.0 との聴き比べ |

- 基準は、フェーズ4で記録した「音程のあるパートを除く基準」（`tests/fixtures/phase3-unpitched.json`）を置き換える。音程のあるパートを含めないと、和声や音程のあるパートの生成器を分けたときの変化を検出できないため
- 大きなファイルを分けるときの目安は行数ではなく、役割の数とする。分けた後のモジュールの名前と分担は設計書で決める
- コメントを書き換えるときは、フェーズの文書を読まなくても理由が分かる文にする。番号やフェーズの名前を、文書へのリンクに置き換えるだけにはしない。文書の構成が変わるとリンクも古くなるため

## アクセシビリティ

WCAG 2.2 の適合レベル AA を目安にします。この音楽アプリでは音そのものが中身なので、聴くための操作（再生・一時停止・停止・音量）と、聴き方を変える操作（パラメーター・ミキサー・共有）を、見えなくても、マウスを使えなくても行えることを優先します。

- **視覚の表示は補助として扱う**: シーケンサー・スペクトラムアナライザー・メーターは、鳴っている音を目で見るためのもの。ステップごとに読み上げると音を聴く邪魔になるので、何を表すかの名前だけを伝える（F-115）
- **メニューは閉じるボタンでだけ閉じる（フェーズ4のまま）**: キーボードでは、メニューの中からフォーカスを閉じるボタンに移して閉じる。メニューはモーダルにしないので、Tab キーでメニューの外の操作部品にも移れる。ただし、メニューに完全に覆われて見えない操作部品には移らない。見えない部品にフォーカスが移ると、どこにフォーカスがあるか分からなくなるため（WCAG 2.2 の 2.4.11）。メニューが画面を覆う狭い画面では、キーボードでは実質モーダルになる
- **既存の部品を活かす**: ボタン、スライダー、チェックボックス、ダイアログには、ブラウザの標準の部品を使い、標準のキー操作をそのまま使う
- 確かめ方: 自動検査のツール（E2E テストの中で）、キーボードだけでの操作、スクリーンリーダー（VoiceOver か NVDA）での読み上げ、コントラスト比の計算

## ブラウザの確認

| ブラウザ | 環境 | 確かめ方 |
| --- | --- | --- |
| Chrome | デスクトップの最新版 | E2E テスト（Chromium）と手動 |
| Edge | デスクトップの最新版 | 手動 |
| Firefox | デスクトップの最新版 | E2E テストと手動 |
| Safari | macOS の最新版 | 手動（E2E テストの WebKit は参考） |
| Safari | iOS の最新版（実機） | 手動 |
| Chrome | Android の最新版（実機） | 手動 |

手動の確認の項目は、再生・一時停止・再開・停止、音の途切れがないこと、メディア操作（OS のメディアキー、ロック画面、通知）、共有のコピー、狭い画面の表示、キーボードでの操作です。

- iOS では、消音のスイッチ、画面のロック、ほかのアプリへの切り替えで、音が止まるかを確かめる。手当ての方法は設計で調べ、手当てできないものは README に書く（F-118）
- ブラウザが音を止めて、ページから再開できないときは、再生を一時停止の状態にして、画面とメディア操作の表示を実際の音に合わせる。止まった音が再生中と表示され続けないようにするため
- 確かめたブラウザの版と結果は、リリースの確認の一覧に記録する

## 仕様の文書

フェーズごとの差分として書いてきた文書を、領域ごとの文書に移します。

```
docs/
├── README.md               # 索引。目的別の入口と読む順番
├── concept.md              # 目的、聴かせ方の考え方、扱わないこと
├── glossary.md             # 用語集
├── architecture.md         # 生成と再生の分離、モジュールと依存方向、生成の流れ、主な型
├── generation/             # random・form・arrangement・harmony・drums・pitched-parts・fx
├── playback/               # transport・sound
├── interface/              # screen・integration
└── quality/                # requirements・testing・release-checklist
```

- **1つの文書の中の並び**: 振る舞い（聞こえ方・見え方としての規則と表）、実装（型、関数の分担、データの流れ）、決めた理由（試聴で確定した値の根拠、採用しなかった案）の順に書く。冒頭に、関係するコードとテストのパスを書く
- **数値の正本**: 調整用の数値の既定値は、コードと `config.example.json` を正本にし、文書には意味・範囲・理由だけを書く。コードの表、進行の表、ステップの重み表のように、何を鳴らすかを決める表は文書に載せる
- **要件の番号**: 引き継がない。文書どうしは、ファイルと見出しへのリンクで参照する
- **受け入れ基準**: 自動で確かめられるものはテストに任せ、文書には残さない。試聴・UI・ブラウザ・アクセシビリティの手動の確認は、`quality/release-checklist.md` にまとめ、リリースのたびに使う
- **ファイル名**: 英語の kebab-case にし、本文は日本語で書く
- **移行表**: 元の文書の見出しごとに、移す先の文書、「後のフェーズで置き換え済み」、「一度きりの作業」のどれかを決めた表を作る。移す内容は新しいフェーズの文書を正とし、古いフェーズからは後で上書きされていない部分だけを拾う。移行表は削除の確認に使い、削除と一緒に消す
- リリースの後の予定と変更の履歴は、GitHub の Issues と Releases で管理する。ロードマップの代わりの文書は作らない

## 配布と CI/CD

| 項目 | 内容 |
| --- | --- |
| 配布先 | GitHub Pages。ユーザーのサイトに独自ドメインが設定してあるので、URL は `https://gh.double-oxygen.net/rholydd-sequencer/` になる |
| base path | `/rholydd-sequencer/`。サンプル・設定ファイル・共有する URL は、すでに base path を基準にしている |
| CI | すべてのブランチへのプッシュとプルリクエストで、型検査・単体テスト・ビルド・E2E テスト |
| CD | main の更新で、CI が通ったら配布する |
| リリース | `v` で始まるタグを main に付け、GitHub Releases に利用者目線のリリースノートを手で書く |

- リポジトリの作成、Pages の有効化、リモートへの push は、利用者が行う
- 設定ファイルは配布しない。配布先ごとに初期値を変えたいときは、利用者が自分でビルドして `config.json` を置く
